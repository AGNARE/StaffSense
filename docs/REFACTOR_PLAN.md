# План перехода к API-first: разделение фронта и бэка без переписывания

Документ отвечает на вопрос «стоит ли разделить проект на фронтенд и бэкенд»
и фиксирует этапы, которые можно делать по одному и пушить отдельно.

## Короткий ответ

**Big-bang SPA сейчас — плохая идея.** Не потому, что SSR «правильный», а потому
что цифры другие:

| Что нужно для переезда | Объём |
|---|---|
| REST-эндпоинтов вместо 88 view-маршрутов | ~60–70 |
| Экранов в новом клиенте | 38 (по прототипу) |
| Строк шаблонов, которые надо переписать | 5 699 |
| Инлайн-стилей, которые надо вынести в дизайн-систему | 285 |
| Новая авторизация для SPA (JWT/CSRF, refresh, роли) | отдельная задача |
| Сборка (Node, bundler, деплой двух артефактов) | новый контур |

Это 4–6 недель плотной работы с потерей работающего демо. Перед конференцией
и защитой — недопустимый риск.

**Правильный путь — «API-first, фронт по модулям»:** сделать бэкенд таким,
чтобы он *мог* отдавать API, и переводить клиент по одному модулю. Тогда
разделение — это последовательность безопасных коммитов, а не один прыжок.

## Целевая структура пакетов

```
com.staffsense
├── api/            ← версионированный REST (/api/v1), только DTO
│   ├── people/     сотрудники, карточка, компетенции
│   ├── risk/       прогнозы, объяснения, пороги
│   ├── work/       проекты, задачи, план-график
│   └── docs/       документы, шаблоны, маршруты
├── domain/         ← бизнес-правила: одна формула = один метод
│   ├── metrics/    workload, kpi, satisfaction
│   ├── risk/       признаки, уровни, пороги
│   └── ...
├── web/            ← Thymeleaf-контроллеры: тонкий адаптер над domain
└── infra/          ← безопасность, планировщики, интеграции
```

Ключевое правило: **`web` и `api` — два адаптера над одним `domain`**.
Пока живёт Thymeleaf, он дергает те же сервисы, что и REST. Никакой логики
в контроллерах.

## Этапы

### Этап 0. Зафиксировать границы (0,5 дня)

- [x] Аудит кода: `docs/CODE_AUDIT.md`
- [x] Замеры связанности: 88 view-эндпоинтов, 0 REST, 285 инлайн-стилей
- [ ] Завести ветку `refactor/api-first` (не трогая `main`)

**Готово, когда:** есть план и ветка; `main` остаётся рабочей демо-версией.

### Этап 1. Тонкие контроллеры (2–3 дня)

- Вынести презентационные модели из контроллеров:
  `RiskController.FeatureCardBuilder` → `domain/risk/FeatureCardService`.
- Убрать `riskScore`-сортировку из памяти: сортировка на уровне запроса.
- Свести расчёт `workload_index` к одному методу (`domain/metrics`), убрать
  дубль из `AttritionMlService`.

**Готово, когда:** контроллеры не содержат формул и текстов для UI,
`mvnw test` зелёный, поведение не изменилось (проверка скриншотами).

### Этап 2. Первый контракт API (3–5 дней)

- `/api/v1/risk` — список прогнозов с фильтрами и пагинацией.
- `/api/v1/risk/{id}` — карточка с факторами.
- OpenAPI-описание (`springdoc-openapi`), версия в пути.
- DTO отдельно от сущностей; никаких `@Entity` в ответах.

**Готово, когда:** страница `/risk` в Thymeleaf рендерится из того же сервиса,
что и API, а API отдаёт те же данные (сверка в тесте).

### Этап 3. Пилотный модуль на отдельном фронте (1–2 недели)

- Берём один модуль — **«Прогноз увольнений»** (он же центральный в докладе).
- Клиент — по прототипу `prototype/risk.html`, собранный как статический
  бандл, ходит только в `/api/v1`.
- Авторизация: cookie-сессия + CSRF (без JWT — проще и безопаснее для SPA
  в том же домене).
- Старые страницы `/risk` остаются, пока новый экран не принят.

**Готово, когда:** модуль работает на новом фронте, старый можно включать
и выключать флагом.

### Этап 4. Миграция по модулям и выпиливание Thymeleaf (по 1 модулю за раз)

Порядок по возрастанию риска:

1. Документы и записки (простые формы, мало связей)
2. Опросы
3. Кадровый процесс и карточка сотрудника
4. Портал онбординга
5. Администрирование

**Готово, когда:** для модуля удалены и Thymeleaf-шаблоны, и view-контроллеры;
API покрыт тестами.

## Что делать НЕ надо

- **Переписывать всё сразу в React/Vue.** Потеряете демо и получите два
  источника правды: DTO и UI-модели.
- **Тянуть JWT «как в микросервисах».** Один домен, одна сессия — хватит
  cookie + CSRF.
- **Переносить дизайн-систему вручную по страницам.** Сначала CSS-токены
  (уже готовы в `prototype/assets/proto.css`), потом компоненты, потом страницы.
- **Делать API «на будущее».** Каждый эндпоинт появляется вместе с экраном,
  который его использует.
