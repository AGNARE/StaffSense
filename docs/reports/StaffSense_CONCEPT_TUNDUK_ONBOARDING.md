## 1. МОДУЛЬ A — «ТУНДУК»: ВЕРИФИКАЦИЯ ПРИ НАЙМЕ

### 1.1 Назначение
При оформлении трудового договора HR вводит ИНН, система получает из госсистемы (эмуляция) персональные данные гражданина и автоматически заполняет личное дело. Ручной ввод и опечатки исключаются.

### 1.2 Сценарий (основной поток)

```
HR → «Принять сотрудника»
  ↓
Ввод ИНН (14 цифр) + подтверждение согласия кандидата на обработку ПДн
  ↓
Проверка формата ИНН
  ├─ не 14 цифр / не цифры → ERR-013, запрос не выполняется
  └─ ок ↓
Обращение к TundukClient (эмуляция)
  ├─ гражданин найден → персональные данные
  ├─ не найден         → ERR-014, разрешён ручной ввод, tunduk_verified=false
  └─ сервис недоступен → ERR-014, ручной ввод, tunduk_verified=false
  ↓
Форма предзаполнена персональными данными (с пометкой «источник: Тундук»)
  ↓
HR дополняет корпоративные поля: отдел, должность, грейд, оклад, руководитель, ёмкость, дата найма, роль
  ↓
Сохранение:
  ├─ ИНН уже есть в системе → РЕАКТИВАЦИЯ существующего сотрудника (BR-023)
  └─ ИНН новый              → создание users + employee_documents
  ↓
Запись в журнал обращений к «Тундук» (аудит ПДн)
  ↓
Личное дело доступно HR/ADMIN
```

### 1.3 Разделение данных: два слоя

| Слой | Источник | Поля | Кто видит |
|---|---|---|---|
| **Персональный** | «Тундук» | ИНН, ПИН, ФИО, дата рождения, пол, паспорт (серия, номер, кем выдан, дата выдачи), адрес регистрации, фото | HR, ADMIN |
| **Корпоративный** | HR | роль, отдел, должность, грейд, оклад, руководитель, ёмкость, дата найма | по матрице доступа |

> «Тундук» знает гражданина, но не знает компанию — поэтому корпоративные поля **никогда** не приходят из внешней системы.

### 1.5 Эмуляция «Тундук»

Архитектура — **порт и адаптер**, чтобы замена на реальный протокол не затронула логику найма:

```
TundukClient (интерфейс)
    └── MockTundukClient (реализация для демонстрации)
            └── справочник тестовых граждан (только вымышленные данные!)
```

**Справочник тестовых ИНН** (детерминированный, ~8–10 записей) + служебные ИНН для проверки ошибок:

| ИНН | Сценарий |
|---|---|
| `12345678901234` | гражданин найден, полный набор данных |
| `12345678901235` … `…42` | другие вымышленные граждане (разные отделы/пол/возраст) |
| `00000000000000` | гражданин **не найден** → ERR-014 |
| `99999999999999` | сервис **недоступен** → ERR-014 |
| `123` | неверная длина → ERR-013 |
| `1234567890123a` | не цифры → ERR-013 |

> ⚠️ Только вымышленные данные. Реальные ИНН и паспорта граждан в репозиторий не попадают.

**Фото:** mock возвращает URL плейсхолдера (например, генерируемая аватарка с инициалами). Архитектурно поле `photo_url` готово к реальному файловому хранилищу — менять модель не придётся.

### 1.6 Бизнес-правила

| ID | Правило |
|---|---|
| **BR-023** | **Реактивация.** Если ИНН уже есть в системе: новый сотрудник не создаётся; существующая учётная запись реактивируется (`active = true`), корпоративные поля обновляются, личное дело актуализируется. HR видит предупреждение «Сотрудник уже есть в системе» с указанием, кто это |
| **BR-024** | **Согласие на ПДн обязательно.** Без отметки о согласии кандидата верификация не выполняется |
| **BR-025** | **Маскирование.** Паспортные данные и ПИН в журналах и для ролей без прав показываются маскированно (`****1234`) |
| **BR-026** | **Аудит.** Каждое обращение к «Тундук» фиксируется в журнале: кто, когда, результат |

### 1.7 Ошибки

| ID | Ситуация | Поведение |
|---|---|---|
| ERR-013 | ИНН не 14 цифр / содержит нецифры | Запрос не выполняется, сообщение «Введите корректный 14-значный ИНН» |
| ERR-014 | Данные не найдены / сервис недоступен | Ручной ввод, `tunduk_verified = false`, запись в журнал |

|---|---|---|---|---|---|
| Приём сотрудника, верификация ИНН | ✓ | ✓ | — | — | — |
| Просмотр личного дела | ✓ | ✓ | — | — | — |

## 2A. МОДУЛЬ C — КАДРОВЫЕ ПРОЦЕССЫ (ТАБЕЛЬ И СЛУЖЕБНЫЕ ЗАПИСКИ)

### 2A.1 Учёт рабочего времени (табель)

**Назначение:** учёт фактически отработанного времени, удалённой работы, больничных и переработок — и передача этих данных в отчёт по итогам месяца.

**Кто что может (по решению заказчика):**

| Действие | EMPLOYEE | PM | HR | ADMIN | EXEC |
|---|---|---|---|---|---|
| Ведение табеля (создание/правка часов) | — | **✓ только своя команда** | **✓ все** | **✓ все** | — |
| Просмотр своего табеля | **✓ (только чтение)** | ✓ | ✓ | ✓ | ✓ |
| Просмотр табеля любой команды | — | ✓ только своя | ✓ | ✓ | ✓ |
| Закрытие месяца / формирование отчёта | — | ✓ своя команда | ✓ | ✓ | — |

> 🔑 **Ключевые правила:**
> 1. Часы вносит **руководитель (PM) по своей команде**; сотрудник свои часы **не редактирует — только читает**. Это отличается от привычной модели «сотрудник заполняет табель сам», поэтому зафиксировано явно.
> 2. HR и ADMIN **редактируют** табель любой команды (не только просматривают).
> 3. Табель за **предыдущий (закрытый) месяц не редактируется** ни PM, ни HR — иначе отчёт перестанет соответствовать данным.

**Модель данных — `work_schedule`**

| Колонка | Тип | Примечание |
|---|---|---|
| `id` | bigint PK | |
| `user_id` | bigint FK → users NOT NULL | чей табель |
| `work_date` | date NOT NULL | день |
| `hours_worked` | numeric(4,2) | фактические часы |
| `is_remote` | boolean NOT NULL default false | удалённая работа |
| `is_sick_leave` | boolean NOT NULL default false | больничный |
| `overtime_hours` | numeric(4,2) default 0 | переработки |
| `created_by_id` | bigint FK → users | кто внёс (PM) |
| `updated_at` | timestamp(6) | |

Уникальность: `(user_id, work_date)` — одна запись на день.

**Период и отчёт.** Месяц считается «периодом»; формируются **два отчёта**:
* по команде PM — для руководителя;
* сводный по компании — для HR.

Оба содержат суммарные часы, переработки, дни удалёнки и больничных.

**Модель данных — `work_schedule_period`** (закрытие месяца)

| Колонка | Тип | Примечание |
|---|---|---|
| `id` | bigint PK | |
| `manager_id` | bigint FK → users NOT NULL | чей участок закрывается |
| `period_start` / `period_end` | date NOT NULL | границы месяца |
| `status` | varchar(20) NOT NULL | OPEN / CLOSED |
| `closed_at` | timestamp(6) | |
| `closed_by_id` | bigint FK → users | |

После закрытия периода правка табеля за этот месяц **блокируется** (иначе отчёт перестанет соответствовать данным).

### 2A.2 Служебные записки

**Назначение:** заявки сотрудника (отпуск, больничный и др.) с согласованием.

**Кто что может:**

| Действие | EMPLOYEE | PM | HR | ADMIN | EXEC |
|---|---|---|---|---|---|
| **Подать записку** | **✓** | **✓** | **✓** | **✓** | **✓** |
| Редактировать свою (до решения) | ✓ | ✓ | ✓ | ✓ | ✓ |
| Отозвать свою (до решения) | ✓ | ✓ | ✓ | ✓ | ✓ |
| Виза руководителя (этап 1) | — | ✓ | — | ✓ | — |
| Утверждение HR (этап 2) | — | — | ✓ | ✓ | — |
| Просмотр своих записок | ✓ | ✓ | ✓ | ✓ | ✓ |
| Просмотр записок команды | — | ✓ | ✓ | ✓ | ✓ |

> 🔑 **Ключевые правила:**
> 1. Подать записку может **любой сотрудник** без исключения.
> 2. Автор может **и редактировать, и отозвать** свою записку, пока она не получила финальное решение.
> 3. Маршрут согласования — строго по ТЗ (`BR-003`): виза руководителя → утверждение HR.

**Модель данных — `service_memo`**

| Колонка | Тип | Примечание |
|---|---|---|
| `id` | bigint PK | |
| `user_id` | bigint FK → users NOT NULL | автор |
| `memo_type` | varchar(30) NOT NULL | VACATION / SICK_LEAVE / OTHER |
| `start_date` / `end_date` | date NOT NULL | период |
| `reason` | text | обоснование |
| `status` | varchar(20) NOT NULL | DRAFT / PENDING_PM / PENDING_HR / APPROVED / REJECTED / CANCELLED |
| `pm_decision_by_id` / `pm_decision_at` | bigint / timestamp | виза руководителя |
| `hr_decision_by_id` / `hr_decision_at` | bigint / timestamp | решение HR |
| `rejection_reason` | text | |
| `created_at` | timestamp(6) NOT NULL | |

**Маршрут согласования** (по `BR-003` ТЗ):
```
DRAFT → PENDING_PM → PENDING_HR → APPROVED
              ↓            ↓
           REJECTED     REJECTED
```
Автор может отозвать записку (`CANCELLED`) до финального решения.

**Влияние на другие модули.** Утверждённый больничный/отпуск должен попадать в табель (дни больничного) и, следовательно, в расчёт нагрузки — это связка, которую надо учесть при реализации.

### 2A.3 Права: сводно

Новый префикс `/timesheet/**` — доступ ADMIN/HR/PM (ведение) и все (свой табель на чтение).
Новый префикс `/memos/**` — доступ всем аутентифицированным (подача и свои записки); визы — по ролям.

### 2A.4 Решения по модулю C (согласовано)

| ID | Вопрос | Решение |
|---|---|---|
| Q-026 | HR и ADMIN редактируют чужие табели? | **Да, редактируют** любые |
| Q-027 | Сотрудник вносит свои часы сам? | **Нет.** Часы вносит только PM по своей команде; сотрудник — только чтение |
| Q-028 | PM правит табель за закрытый месяц? | **Нет.** За предыдущий (закрытый) период правка запрещена (BR-028) |
| Q-029 | Отчёт в конце месяца | **Оба:** по команде PM и сводный по компании для HR |
| Q-030 | Маршрут записок | **По ТЗ** (BR-003): виза PM → утверждение HR |
| Q-031 | Автор правит записку после подачи? | **И редактирует, и отзывает** — пока нет финального решения |
| Q-032 | Отпуск/больничный учитывается в нагрузке? | **Да**, автоматически: утверждённая записка → табель → расчёт нагрузки |

## 3. ЮРИДИЧЕСКАЯ ЧАСТЬ (для пояснительной записки)

Обоснование подхода «HR инициирует верификацию»:

1. Персональные данные обрабатываются **с согласия субъекта** — кандидат подписывает согласие при приёме на работу (`consent_given_at` в личном деле, `BR-024`).
2. Обработка имеет **конкретную цель** — оформление трудового договора и ведение личного дела; данные не используются для иных целей.
3. Действует принцип **минимизации**: из госсистемы запрашивается только то, что нужно для трудоустройства.
4. **Ограничение доступа**: паспортные данные и ПИН доступны только HR/ADMIN (`BR-025`), ведётся **журнал обращений** (`BR-026`) — это позволяет установить, кто и когда смотрел данные.
5. **Срок хранения** и порядок уничтожения определяются внутренним регламентом компании (в ТЗ — открытый вопрос `Q-018`).
6. В демонстрационной версии используются **только вымышленные данные** граждан.

## 5. КРИТЕРИИ ГОТОВНОСТИ

* HR может принять сотрудника, введя ИНН, и увидеть заполненные персональные данные.
* Повторный приём по тому же ИНН реактивирует существующую запись, дубль не создаётся.
* Некорректный ИНН, «не найден» и «сервис недоступен» обрабатываются с понятными сообщениями.
* Каждое обращение к «Тундук» попадает в журнал.
* Паспорт маскируется для ролей без прав.
* Любой сотрудник читает портал; править статьи может только HR/ADMIN.
* В справочнике сотрудников **нет** окладов, KPI и прогнозов риска.
* Чек-лист новичка сохраняет отметки персонально для каждого сотрудника.
* PM вносит часы **только по своей команде**; сотрудник видит свой табель **только на чтение**.
* Табель за закрытый месяц не редактируется; отчёт формируется по итогам месяца.
* Подать служебную записку может **любой** сотрудник; маршрут согласования соблюдается.
* Все миграции применяются Flyway; `ddl-auto=validate` проходит.
* Тесты зелёные (Java + Python).

### Изменение статуса FR-030
FR-030 в ТЗ описан как «портал кандидата» (кандидат сам вводит ИНН). По решению заказчика **инициатором выступает HR**, поэтому FR-030 переформулируется и раскрывается в FR-040 + FR-041. Отдельная роль `CANDIDATE` и сущность `candidates_onboarding` **не требуются** (вопрос `Q-002` закрывается: роль не нужна).
