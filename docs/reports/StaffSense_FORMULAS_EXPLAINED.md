# STAFFSENSE — ФОРМУЛЫ: КАК СЧИТАЕТСЯ РИСК, KPI И НАГРУЗКА

**Назначение документа.** Объяснить «человеческим языком», какие формулы используются в системе, откуда они взялись, как проверить расчёт вручную и насколько они логичны. Документ написан после завершения работ, поэтому описывает **фактическое** состояние кода.

**Коротко о главном:**
* Риск увольнения считает **Python-модель** (логистическая регрессия). Java только собирает 7 чисел-признаков и отправляет их.
* Формулы-«дефициты» нужны **только для генерации учебного датасета**, на котором модель учится. Сама модель знаки и веса **находит сама**.
* Если ML недоступен, Java считает риск по простой эвристике (5 строк).
* KPI и нагрузка — отдельные формулы, не связанные с риском напрямую (они лишь поставляют признаки).

## 2. СЕМЬ ПРИЗНАКОВ (вход модели)

Все признаки приводятся к диапазону **0…1** (кроме двух — см. ниже), потому что логистическая регрессия чувствительна к масштабу.

| № | Признак | Формула | Смысл: 0 → 1 |
|---|---|---|---|
| 1 | `salary_ratio` | `зарплата / средняя зарплата по тому же грейду` | 0 — сильно ниже рынка; 1 — на уровне |
| 2 | `workload_index` | последняя `WorkloadRecord` **или** `Σ estimateHours активных задач / weeklyCapacityHours` | 1.0 — норма; >1.3 — перегруз |
| 3 | `kpi_norm` | `min(kpiScore / 100, 1)` | 0 — плохой KPI; 1 — отличный |
| 4 | `tenure_months_norm` | `min(месяцев_с_hireDate / 60, 1)` | 0 — новичок; 1 — 5+ лет |
| 5 | `satisfaction_norm` | `min(средний_LIKERT_за_90_дней / 5, 1)` | 0 — очень недоволен; 1 — очень доволен |
| 6 | `missed_1on1_ratio` | `пропущенные_встречи / все_встречи` | 0 — не пропускает; 1 — пропускает всё |
| 7 | `overtime_norm` | `min(overtimeHours / (weeklyCapacityHours × 0.2), 1)` | 0 — нет переработок; 1 — на пределе |

**Значения по умолчанию**, если данных нет: `kpi_norm = 0.7`, `satisfaction_norm = 0.65`, `missed_1on1_ratio = 0`, `overtime_norm = 0`, `salary_ratio = 1.0`.

### Пример расчёта вручную
Сотрудник: зарплата 85 000, средняя по грейду MIDDLE — 100 000; активных задач на 60 ч, ёмкость 40 ч/нед; KPI 62; нанят 24 месяца назад; средний балл опросов 2.4; из 10 встреч пропущено 3; переработки 6 ч.

```
salary_ratio       = 85000 / 100000 = 0.85
workload_index     = 60 / 40        = 1.50   (>1.3 — перегруз)
kpi_norm           = 62 / 100       = 0.62
tenure_months_norm = 24 / 60        = 0.40
satisfaction_norm  = 2.4 / 5        = 0.48
missed_1on1_ratio  = 3 / 10         = 0.30
overtime_norm      = 6 / (40×0.2)   = 6 / 8 = 0.75
```

### ⚠️ Расхождение, которое важно знать
`salary_ratio` и `overtime_norm` считаются **по-разному** в двух местах:

| | `AttritionMlService` (реальные прогнозы) | `DataInitializer` (сид-прогнозы) |
|---|---|---|
| `salary_ratio` | средняя зарплата **из базы** по грейду | **константы** 55 000 / 80 000 / 110 000 / 150 000 |
| `overtime_norm` | делится на `ёмкость × 0.2` = **8 ч** | делится на **20 ч** (жёстко) |
| `satisfaction_norm` | **реальные** ответы опросов | **случайное** число |

**Следствие:** 16 прогнозов, создаваемых при первом запуске, и прогнозы после нажатия «Пересчитать» считаются по разным формулам признаков. Это исторический дефект; единая формула — задача на доработку.

## 3. КАК ИЗ ПРИЗНАКОВ ПОЛУЧАЕТСЯ РИСК

### 3.1 Стандартизация (StandardScaler)
Перед подачей в модель признаки преобразуются:

```
x' = (x − среднее_по_обучающей_выборке) / стандартное_отклонение
```

**Зачем:** у `salary_ratio` разброс ~0.25, у `workload_index` ~0.35. Без стандартизации модель решила бы, что «более крупный» признак важнее.

**Важно:** средние и отклонения берутся из **обучающего датасета** и сохраняются в `model/scaler.pkl`. Если датасет изменится, а scaler не переобучится — расчёт поедет.

### 3.2 Логит и сигмоида
```
z = b0 + b1·x'1 + b2·x'2 + … + b7·x'7      (логит, любое число)
p = 1 / (1 + e^(−z))                        (сигмоида, 0…1)
riskScore = p × 100
```

Коэффициенты `b0…b7` **находит сама модель** при обучении (`model.coef_`, `model.intercept_`). Их не задаёт программист.

Для справки, фактические веса из `model/weights.json`:
```
b0 = −0.0152   b1 (salary)     = −0.1229   b2 (workload)   = +0.1682
b3 (kpi)       = −0.2409      b4 (tenure)   = −0.1958
b5 (satisf)    = −0.1908      b6 (missed)   = +0.0674   b7 (overtime) = +0.1856
```
**Как читать знаки:** минус у зарплаты/KPI/стажа/удовлетворённости означает «чем выше — тем ниже риск». Плюс у нагрузки/пропусков/переработок — «чем выше, тем выше риск». **Это логично и соответствует здравому смыслу.**

### 3.3 Уровни риска
```
riskScore < 33          → LOW
33 ≤ riskScore < 66     → MEDIUM
riskScore ≥ 66          → HIGH
```
Пороги лежат в трёх местах (Python, Java-fallback, генератор) и в `application.yml` (`risk.thresholds`), но **конфиг кодом не читается** — значения задублированы. Уровня `CRITICAL` не существует (он есть только у приоритета задачи).

### Пример расчёта вручную (продолжение)
Пусть после стандартизации получены `x'`, и модель дала `z = 1.42`:
```
p = 1 / (1 + e^(−1.42)) = 1 / (1 + 0.2417) = 0.8053
riskScore = 80.53 → HIGH
```

## 4. ФОРМУЛА ГЕНЕРАЦИИ ДАТАСЕТА (дефицитная форма)

Это **не** формула прогноза. Она нужна, чтобы создать учебные примеры, на которых модель учится.

Сначала признак превращается в «дефицит» — насколько он хуже идеала:
```
дефицит_зарплаты       = 1 − salary_ratio
дефицит_нагрузки       = max(workload_index − 1.0, 0)     ← норма = 1.0, ниже нормы дефицита нет
дефицит_KPI            = 1 − kpi_norm
дефицит_стажа          = 1 − tenure_months_norm
дефицит_удовлетворённости = 1 − satisfaction_norm
дефицит_пропусков      = missed_1on1_ratio
дефицит_переработок    = overtime_norm
```

Затем:
```
z = −1.5
  + 1.2·дефицит_зарплаты
  + 1.0·дефицит_нагрузки
  + 0.8·дефицит_KPI
  + 0.6·дефицит_стажа
  + 1.1·дефицит_удовлетворённости
  + 0.9·дефицит_пропусков
  + 0.7·дефицит_переработок

p = 1/(1+e^(−z))
risk_score = p × 100
attrition  ~ Bernoulli(p)     ← метка «уволится/нет» сэмплируется случайно
```

### Почему «дефицитная форма» логичнее исходной
**Было (ошибка):** веса умножались на *сырые* признаки с плюсом:
`z = −1.5 + 1.2·salary + 1.0·workload + 0.8·kpi + …`
Это означало: **чем выше зарплата, KPI, стаж и удовлетворённость — тем выше риск увольнения.** То есть модель училась на перевёрнутой логике.

**Стало:** вычитание из единицы разворачивает смысл — «чем больше не хватает, тем выше риск». Теперь связь правильная.

**Проверено тестом:** `DatasetGeneratorTest.lowerSalaryImpliesHigherRisk` — средний риск у сотрудников с зарплатой ниже 0.8 **выше**, чем у сотрудников с зарплатой выше 1.2.

### Что здесь спорно
* Веса (1.2, 1.0, 0.8, 0.6, 1.1, 0.9, 0.7) и смещение (−1.5) — **экспертные, не обоснованные данными**. Это нормально для учебного проекта, но на защите стоит говорить честно: «веса заданы вручную, чтобы получить правдоподобное распределение».
* Метка `attrition` **шумная** (сэмплируется по вероятности), поэтому 100 % точности недостижимо в принципе. Accuracy ≈ 0.69 — ожидаемый результат для таких данных.
* Метрики считаются на **обучающей** выборке (in-sample), отложенная выборка не используется. Это завышает оценку качества.

## 5. ОБЪЯСНЕНИЕ ПРОГНОЗА (XAI)

Для каждого признака считается «дефицит» и умножается на 100:
```
impact = дефицит × 100        (шкала 0…100)
```
Показываются **до 3** факторов с наибольшим `impact`.

### ⚠️ Здесь есть концептуальная слабость
`impact` **не использует коэффициенты модели**. То есть если модель выучила, что `missed_1on1_ratio` важнее всего, а `overtime_norm` — почти не важен, объяснение всё равно покажет оба с их «дефицитами». Формально это не объяснение модели, а **повторение входных данных** в другой шкале.

**Более корректный подход:** `impact = coef_i × x'_i` (вклад в логит). Такой расчёт есть в `model.py` (в удалённом legacy-сервисе), но в текущем `services.py` он заменён на дефицитный.

**Вывод:** для учебного проекта текущий вариант приемлем и нагляден, но на защите нельзя утверждать, что это «объяснение решения модели». Честная формулировка: «показываем, какие признаки у сотрудника отклоняются от нормы».

## 6. РЕЗЕРВНЫЙ РАСЧЁТ (когда ML недоступен)

Если Python-сервис не ответил за 2 секунды, Java считает так:
```
score = 50
если workload_index > 1.3      → score += 15
если salary_ratio  < 0.9       → score += 10
если satisfaction_norm < 0.5   → score += 10
score = min(score, 95)
уровень: ≥66 HIGH, ≥33 MEDIUM, иначе LOW
```

**Логичность:** грубо, но осмысленно — учитывает три главных фактора. Ограничение 95 не даёт эвристике «приговорить» сотрудника со 100 %.

**Особенности:**
* Минимум `score` = 50, поэтому **LOW по эвристике недостижим** — сотрудник без единого «плохого» признака всё равно получит MEDIUM.
* Ветка `+15` срабатывает редко: индекс нагрузки из сид-данных редко превышает 1.3.
* У Python-сервиса **свой** резерв: если нет `model.pkl`, он считает сигмоиду по `weights.json`. Это **другая** формула, чем у Java. Пользователь может получить разные оценки в зависимости от того, что именно сломалось.

## 7. KPI

```
onTimeRate = задачи, завершённые не позже dueDate / все завершённые за период
reopenRate = сумма reopenedCount / число завершённых задач
```

Далее — два варианта:

**Если оценка руководителя НЕ задана** (вес 0.3 перераспределяется на остальные):
```
KPI = (0.5·onTimeRate·100 + 0.2·(100 − min(reopenRate·100, 100))) / 0.7
```

**Если оценка задана (1…5):**
```
managerNorm = (оценка − 1) / 4 × 100        ← шкала 1..5 → 0..100
KPI = (0.5·onTime·100 + 0.2·(100 − reopen·100) + 0.3·managerNorm) / 1.0
```

### Пример (контрольный из ТЗ, TC-017)
`onTimeRate = 0.75`, `reopenRate = 0.25`, оценки нет:
```
= (0.5 × 75 + 0.2 × (100 − 25)) / 0.7
= (37.5 + 15) / 0.7
= 52.5 / 0.7 = 75.0
```
Этот пример закреплён тестом `KpiCalculationServiceTest.withoutManagerRatingMatchesSpecFormula`.

**Логичность:** формула разумна — вовремя закрытые задачи поощряются, переоткрытия штрафуются. **Спорный момент:** `reopenRate` может превысить 1 (одна задача переоткрыта 4 раза → 4.0), поэтому стоит ограничение `min(…, 100)`.

**Целесообразность:** вес оценки руководителя (0.3) — самый субъективный компонент. Сейчас он используется, только если оценку кто-то проставил; **эндпоинта/формы для ввода оценки пока нет** (задача на доработку).

## 8. НАГРУЗКА

```
totalEstimatedHours = Σ estimateHours задач, где исполнитель = сотрудник
                      и статус ≠ DONE, и задача попадает в период
weeks         = max(1, недель между началом и концом периода)
capacityHours = weeklyCapacityHours × weeks
workloadIndex = totalEstimatedHours / capacityHours
```

**Учёт периода** (добавлено): задача учитывается, если создана не позже конца периода и не завершена до его начала.

**Категории (BR-002):** <0.6 недогруз · 0.6–1.0 норма · 1.0–1.3 повышенная · >1.3 перегруз.

### Пример
Период — октябрь (4 недели), ёмкость 40 ч/нед, активных задач на 134 ч:
```
capacityHours = 40 × 4 = 160
workloadIndex = 134 / 160 = 0.8375
```
Такой расчёт виден в логе приложения после изменения статуса задачи.

**Логичность:** формула прозрачна. **Ограничение:** `ChronoUnit.WEEKS.between` **округляет вниз**, поэтому период 13 дней = 1 неделя (ёмкость занижается, индекс завышается). Для месяца (30–31 день) это даёт 4 недели вместо ~4.4 — индекс завышается примерно на 10 %.

## 9. СВОДНАЯ ОЦЕНКА: ЧТО ЛОГИЧНО, ЧТО СПОРНО

### ✅ Логично и целесообразно
1. **Направление влияния признаков** — низкая зарплата, низкий KPI, низкая удовлетворённость, перегруз, пропуски встреч повышают риск. Совпадает со здравым смыслом.
2. **Нормализация признаков и StandardScaler** — обязательны для логистической регрессии.
3. **Пороги 33/66** — просты и объяснимы.
4. **Дефицитная форма в генераторе** — после исправления логика верна.
5. **Формула KPI** — прозрачна, поощряет своевременность и штрафует переоткрытия.
6. **Fallback** — система остаётся работоспособной без ML.

### ⚠️ Спорно / требует доработки
1. **XAI не использует веса модели** — это «отклонения от нормы», а не объяснение прогноза.
2. **Три разных источника оценки риска** (ML, Java-эвристика, Python-fallback) дают разные числа при одном и том же сотруднике.
3. **Разные формулы признаков** в `AttritionMlService` и `DataInitializer` (`overtime` делится на 8 и на 20; зарплата — динамическая и константная).
4. **Метрики только in-sample** — реальное качество неизвестно.
5. **Пороги задублированы** в четырёх местах вместо чтения из `application.yml`.
6. **`ChronoUnit.WEEKS` округляет вниз** — индекс нагрузки систематически завышен.
7. **Экспертные веса** (1.2, 1.0, …) не обоснованы данными.
8. **Эвристика не может дать LOW** (минимум 50).
9. **`managerRating` негде ввести** через интерфейс.

### 🔎 Что стоит сказать на защите
* Модель — **логистическая регрессия**, коэффициенты выучены на синтетическом датасете 700 записей; accuracy ≈ 0.69 (на обучающей выборке).
* Датасет **синтетический**; связь «признак → увольнение» задана формулой с экспертными весами, а не взята из реальных HR-данных.
* Прогноз носит **вспомогательный характер** и не должен быть единственным основанием кадрового решения (этический аспект, раздел 26.3 ТЗ).

## 10. ЧТО БЫЛО ИСПРАВЛЕНО В ФОРМУЛАХ

| Проблема | Было | Стало |
|---|---|---|
| Разделитель в CSV | запятая (локаль ru-RU) → датасет нечитаем | `Locale.US`, всегда точка |
| Знаки признаков в генераторе | высокая зарплата/KPI/стаж повышали риск | дефицитная форма, направление верное |
| Колонка метки | только `risk_score` | добавлена `attrition` (как в Python) |
| Веса KPI | хардкод, `managerRating` игнорировался | читаются из `kpi.weights.*`, оценка учитывается |
| Период нагрузки | не учитывался | задача проверяется по датам создания/завершения |
| Пересчёт KPI/нагрузки | не вызывался вообще | вызывается при изменении задачи |
| Деление на нулевую ёмкость | `Infinity`/`NaN` | возвращается 0 |
