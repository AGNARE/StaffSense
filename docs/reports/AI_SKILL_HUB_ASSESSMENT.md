## Резюме

E-08 «AI Skill Hub» — реестр корпоративных ИИ-скиллов в формате `SKILL.md` (YAML-frontmatter + системная инструкция + шаблоны переменных), каталог скиллов по IT-ролям и вызов скилла из карточки задачи с выводом ответа ИИ в комментариях (FR-033, FR-034; BG-05). В коде модуль отсутствует полностью: поиск по `skill`/`SKILL`/`ai_skills`/`agent_roles` по `demo/src` не даёт ни одного совпадения, в `Task` нет ни `tech_stack`, ни комментариев, миграций и таблиц нет. Оба требования имеют приоритет SHOULD в Фазе 3, при этом модуль заблокирован открытым вопросом Q-016 (источник `tech_stack` и выбор ИИ-провайдера/модели) и внешней зависимостью от ИИ-оркестратора, для которого ТЗ допускает только эмуляцию. Вывод: делать модуль стоит, но **в урезанном MVP-объёме** (вариант B) — полный объём по ТЗ оправдан только после закрытия Q-016 и появления реального оркестратора, поскольку в текущем виде FR-034 нельзя принять формально (HTMX в кодовой базе отсутствует, карточки задачи как экрана нет).

### Наблюдения по тексту ТЗ

1. **Обе требований — SHOULD, а не MUST.** FR-033 и FR-034 помечены «SHOULD / План (Фаза 3)»; в MoSCoW-разделе они в блоке SHOULD HAVE. Формального обязательства поставки нет.
2. **Расхождение нумерации эпика.** В разделе 9 эпик назван «Эпик E-08. AI Skill Hub [План]», а в разделе 38 тот же эпик идёт как «EP-09 AI Skill Hub», тогда как «EP-08» там же обозначает «Онбординг, табель, записки». То есть E-08 и EP-09 — один и тот же модуль F-15; в документации следует использовать оба ID.
3. **Открытый вопрос Q-016 блокирует оба требования.** Он прямо привязан к FR-033 и FR-034, владелец — «Автор», то есть это не вопрос к заказчику, а внутреннее архитектурное решение, которое может быть принято без ожидания внешнего ответа.
4. **Пробелы ТЗ (в ТЗ не описано):**
   - нет NFR (производительность, лимиты, аудит, безопасность) для E-08 — поиск по ТЗ не даёт ни одного NFR, связанного с FR-033/FR-034;
   - в ТЗ не описано, где хранятся ответы ИИ: «комментарии задачи» упоминаются (FR-034, UC-014, SCREEN-027, TC-044), но сущность/таблица комментариев в модели данных раздела 19 отсутствует;
   - в ТЗ не описано, как определяется IT-роль сотрудника (BACKEND, FRONTEND, QA, PM, ANALYST): в системе роли — ADMIN, EXEC, HR, PM, EMPLOYEE, а справочник IT-ролей заявлен только как таблица `agent_roles` — источник значения не указан;
   - в ТЗ не описано, где физически хранится файл `SKILL.md` и по какому пути заполняется `skill_file_path` (только поле в `ai_skills`);
   - в ТЗ не описано, что такое «JSON-схема» из BR-005 и где она задаётся;
   - в ТЗ не описано содержимое обязательных секций («манифест, промпт, роли» — BR-005), кроме перечня полей frontmatter в FR-033;
   - в ТЗ не описано поведение при отсутствии у задачи `tech_stack` сверх пометки «[ТРЕБУЕТ УТОЧНЕНИЯ: источник значения]»;
   - в ТЗ не описано, как ответ ИИ связан с задачей (отдельная сущность комментария, поле, или иное) и можно ли редактировать/удалять ответ;
   - SCREEN-027 заявлен с маршрутом «не определён», а в разделе 24 «Состояния UI» экран AI Skill Hub вообще не перечислен, хотя SCREEN-027 объявляет состояния Default, Loading, Error.
5. **Коллизия ID ERR-015.** Дополнение к ТЗ переиспользует `ERR-015` под ситуацию «Правка табеля за закрытый период»; это зафиксировано в `docs/reports/TZ_TRACEABILITY_BR_ERR.md`. При приёмке сообщение ERR-015 ТЗ («Скилл не может быть выполнен: причина») надо проверять именно по ТЗ, а не по дополнению.
6. **`agent_roles` вне CRUD-матрицы.** В примечании к CRUD-матрице перечислены плановые сущности, включая `ai_skills`, но `agent_roles` в этом перечне отсутствует — права на неё в ТЗ не описаны.
7. **Зависимости.** FR-033 зависит от FR-004 («Ролевой доступ (RBAC)», MUST, «Частично реализовано»); FR-034 — от FR-033 и FR-008 («Канбан-доска проекта», MUST, «Реализовано»). То есть FR-034 технически опирается на уже существующую доску, а FR-033 — на существующий RBAC-каркас.

## Варианты решения

### Вариант A — полная реализация по ТЗ

Объём: все артефакты разделов 1–9 выше, включая валидацию JSON-схемы (BR-005), загрузку файла `SKILL.md` через UI, каталог по пяти IT-ролям, HTMX-вызов из карточки задачи, новый экран карточки задачи, отдельное хранение ответов ИИ, эмуляцию оркестратора с заделом под реального провайдера, ~10 тестов, миграция V7, документация.

- **Плюсы:** полное соответствие FR-033, FR-034, US-035, US-036, UC-014, UC-016, SCREEN-027, BR-005, ERR-015, TC-043, TC-044; закрывает BG-05 и F-15 целиком; снимает единственный «полностью отсутствующий» эпик из отчёта трассируемости; даёт задел под реальный оркестратор.
- **Минусы:** формально требует ответов, которых в ТЗ нет (источник `tech_stack`, что такое JSON-схема, где хранится `SKILL.md`, как определяется IT-роль, как хранить комментарии); тянет за собой сквозную инфраструктуру HTMX, которой в проекте нет (R-11), и новый экран карточки задачи; при одном исполнителе (R-03) конкурирует с MUST-доработками безопасности; реалистичная приёмка «по ТЗ» невозможна до закрытия Q-016, а заявленного контракта оркестратора не существует.
- **Оценка:** **2 итерации** (диапазон 1,5–2).

### Вариант B — MVP

Сохраняется ядро ценности: реестр `SKILL.md` с парсингом и базовой валидацией + вызов скилла из карточки канбана с ответом в комментариях.

- **Что сохранить:** таблицы `ai_skills` и `agent_roles` по ТЗ; парсер YAML-frontmatter (название, описание, `agent_roles`), системная инструкция, шаблоны переменных; валидация обязательных секций «манифест, промпт, роли» (BR-005) с отклонением и описанием (ERR-015); каталог по IT-ролям; `AISkillService` + `/skills` + `/tasks/{id}/skills/{skillId}/run` по предложению API ТЗ; подстановка `title`/`description`; вызов эмулятора оркестратора; запись ответа в комментарии задачи; RBAC ADMIN/просмотр; миграция V7; тесты на парсер/валидатор/вызов.
- **Что урезать:** валидация «JSON-схемы» (в ТЗ не описана — отложить до уточнения); загрузка файла через UI — сидировать каталог через миграцию/`DataInitializer` по образцу `OnboardingContentInitializer`, ADMIN-форма загрузки во вторую очередь; `tech_stack` — подставлять только при заполненном поле, поле добавить в `Task`, но правило заполнения вынести в отдельное решение после Q-016; HTMX-запрос заменить на обычный POST + redirect/фрагмент через существующий серверный рендеринг (HTMX в проекте отсутствует); отдельный экран карточки задачи не создавать — точка вызова в existing `projects/board.html`; состояния Loading/Error — минимальные; один шаблон каталога вместо двух.
- **Плюсы:** покрывает FR-033 и FR-034 по существу и делает US-035/US-036, UC-014/UC-016, TC-043/TC-044, BR-005, ERR-015 проверяемыми; не блокируется полностью Q-016 (решение по `tech_stack` можно принять внутри); не тянет HTMX и новый экран; укладывается примерно в одну итерацию; при появлении реального оркестратора добавляется один клиент без переделки модели данных.
- **Минусы:** формально FR-034 в части «HTMX-запрос» не выполняется буквально (это уже зафиксированный в ТЗ риск R-11 по другому требованию); валидация JSON-схемы из BR-005 не реализуется (BR-005 останется частично покрытым); SCREEN-027 в части «Actions: загрузить SKILL.md» покрывается только если оставить ADMIN-форму — иначе частично.
- **Оценка:** **0,75–1 итерация** (≈ 3 сервиса/контроллера, 1 миграция с 3 таблицами, 2–3 шаблона, 8–10 тестов).

## Рекомендация

**Рекомендуется вариант B — MVP, оценка 0,75–1 итерация** (порядка одной итерации, сравнимой с модулем табеля), с явным исключением из текущей поставки валидации «JSON-схемы» из BR-005 и буквального HTMX-запроса из FR-034.

Обоснование:

1. **Ценность достигается при малом объёме.** Ядро эпика — реестр `SKILL.md` (FR-033) и вызов скилла из карточки задачи (FR-034). Обе функции реализуемы на существующей инфраструктуре: RBAC-каркас есть (`SecurityConfig.java`), образец вызова внешнего сервиса есть (`AttritionMlService.java`), образец сидирования справочников есть (`OnboardingContentInitializer.java`), канбан-доска есть (`projects/board.html`).
2. **Полный вариант A заблокирован, а не просто дорог.** Валидация JSON-схемы, источник `tech_stack`, место хранения `SKILL.md` и контракт оркестратора — этого нет в ТЗ, и Q-016 (владелец — Автор) прямо блокирует FR-033/FR-034. Делать вариант A сейчас означает проектировать за ТЗ.
3. **MVP снимает главный дефект документации.** Сейчас E-08 — единственный эпик, полностью отсутствующий в коде, и это зафиксировано в `TZ_TRACEABILITY_FR_NFR.md` и `TZ_TRACEABILITY_BR_ERR.md`. После варианта B FR-033 закрывается полностью, FR-034 — по существу, а TC-043/TC-044/BR-005/ERR-015/SCREEN-027 становятся проверяемыми; остаются лишь точечные отклонения, которые можно оформить как согласованные.
4. **Вариант C нежелателен.** Он даёт нулевую стоимость, но теряет BG-05 и два пункта из блока SHOULD HAVE, тогда как в ТЗ нет обоснования для переноса их в COULD. Кроме того, при возврате к модулю модель данных создаётся с нуля, и экономия обнуляется.
5. **Порядок действий.** Сначала закрыть Q-016 в минимальном объёме (источник `tech_stack` + решение «оркестратор = эмуляция»), затем сделать миграцию V7 и парсер с валидацией (этапы 1–2), затем вызов из карточки (этап 3), затем ошибки/RBAC/состояния (этап 4) и тесты с обновлением отчётов трассируемости (этап 5). Веса модели (Q-004) в промпт скиллов не закладывать.

**Итоговая оценка объёма: 0,75–1 итерация по варианту B** (A — 1,5–2 итерации; C — 0). Точность оценки ограничена тремя неизвестными, которых нет в ТЗ: структура хранения комментариев, правила определения IT-роли и способ работы с `skill_file_path`.
