## 1. НАЗНАЧЕНИЕ ДОПОЛНЕНИЯ

В ходе реализации выявлено, что часть функциональности либо отсутствовала в ТЗ, либо была описана недостаточно полно. Дополнение фиксирует:

* четыре новых модуля (Модуль A — «Тундук», Модуль B — портал онбординга, Модуль C — кадровые процессы);
* переформулировку требования `FR-030` исходного ТЗ;
* закрытие ранее открытых вопросов `Q-002`, `Q-015`, `Q-018`;
* новые открытые вопросы `Q-024…Q-032`;
* переход на версионирование схемы БД (Flyway).

## 2. УТОЧНЕНИЕ ТЕРМИНОЛОГИИ (устраняет путаницу исходного ТЗ)

В ТЗ v1.0 слово «онбординг» использовалось в трёх разных смыслах. Устанавливается однозначная терминология:

| Термин | Определение | Модуль |
|---|---|---|
| **«Тундук», верификация по ИНН** | Запрос персональных данных гражданина КР в госсистеме при приёме на работу и автозаполнение личного дела | **A** |
| **Портал онбординга** | Внутренний справочник компании: ценности, структура, должностные инструкции, регламенты, FAQ, чек-лист новичка | **B** |
| **Опрос адаптации** | `SurveyType.ONBOARDING` — шаблон опроса из модуля опросов (реализован ранее) | опросы |

> Термин «портал кандидата» из ТЗ v1.0 **не используется**: инициатором верификации выступает HR, а не кандидат.

## 3. МОДУЛЬ A — ВЕРИФИКАЦИЯ ПО ИНН («ТУНДУК»)

### 3.1 Переформулировка FR-030

**Было (ТЗ v1.0):** «Онбординг кандидата по ИНН (Тундук, mock)» — кандидат самостоятельно вводит ИНН на портале кандидата; хранение в `candidates_onboarding`.

**Стало:** FR-030 раскрывается в два требования (FR-040, FR-041). Инициатор — **HR** при оформлении трудового договора. Отдельная роль `CANDIDATE` и сущность `candidates_onboarding` **не требуются**.

### 3.2 Новые функциональные требования

| ID | Название | Приоритет | Статус |
|---|---|---|---|
| **FR-040** | Верификация гражданина по ИНН («Тундук», mock): проверка формата, запрос данных, автозаполнение формы приёма | MUST | **Реализовано** |
| **FR-041** | Личное дело сотрудника: персональные данные, фото, согласие на обработку ПДн | MUST | **Реализовано** |

**Состав данных, получаемых из госсистемы:** ИНН, ПИН, ФИО, дата рождения, пол, паспорт (серия, номер, кем выдан, дата выдачи), адрес регистрации, фотография.

**Состав корпоративных данных (заполняет HR):** роль, отдел, должность, грейд, оклад, руководитель, недельная ёмкость, дата найма, пароль.

### 3.3 Новые бизнес-правила

| ID | Правило | Описание |
|---|---|---|
| **BR-023** | Реактивация при повторном приёме | Если ИНН уже есть в системе, новый сотрудник не создаётся: существующая учётная запись реактивируется (`active = true`), корпоративные и персональные данные обновляются |
| **BR-024** | Обязательное согласие на обработку ПДн | Без отметки о согласии кандидата верификация и приём не выполняются; момент согласия фиксируется в личном деле |
| **BR-025** | Маскирование персональных данных | Паспорт и ИНН отображаются маскированно (`****1234`) для ролей без прав и в журналах приложения |
| **BR-026** | Аудит обращений к «Тундук» | Каждый запрос фиксируется: кто, когда, по какому ИНН, результат |

### 3.4 Новые ошибки

| ID | Ситуация | Поведение | Статус |
|---|---|---|---|
| **ERR-013** | ИНН не состоит из 14 цифр | Запрос не выполняется; сообщение «Введите корректный 14-значный ИНН (только цифры)»; запись в журнал с результатом `INVALID` | **Реализовано** |
| **ERR-014** | Гражданин не найден / сервис недоступен | Разрешён ручной ввод; `tunduk_verified = false`; запись в журнал (`NOT_FOUND` / `UNAVAILABLE`) | **Реализовано** |

## 5. МОДУЛЬ C — КАДРОВЫЕ ПРОЦЕССЫ

### 5.1 Учёт рабочего времени (табель)

| ID | Название | Приоритет | Статус |
|---|---|---|---|
| **FR-045** | Внесение часов руководителем по своей команде | MUST | **Реализовано** |
| **FR-046** | Просмотр своего табеля сотрудником (только чтение) | MUST | **Реализовано** |
| **FR-047** | Закрытие месяца и отчёты по табелю | SHOULD | **Реализовано** |

**Новые бизнес-правила:**

| ID | Правило |
|---|---|
| **BR-027** | Табель ведёт **руководитель по своей команде**; HR и ADMIN правят табель любой команды; сотрудник свои часы **не редактирует** — только просматривает |
| **BR-028** | Табель за **закрытый период не редактируется** (иначе отчёт перестанет соответствовать данным) |

**Отчёты (оба обязательны):** по команде руководителя — для PM; сводный по компании — для HR.

**Модель данных:**

* `work_schedule`: `id`, `user_id` (FK), `work_date`, `hours_worked`, `is_remote`, `is_sick_leave`, `is_vacation`, `overtime_hours`, `created_by_id` (FK), `updated_at`; UNIQUE (`user_id`, `work_date`)
* `work_schedule_period`: `id`, `manager_id` (FK), `period_start`, `period_end`, `status` (`OPEN`/`CLOSED`), `closed_at`, `closed_by_id` (FK); UNIQUE (`manager_id`, `period_start`, `period_end`)

### 5.2 Служебные записки

| ID | Название | Приоритет | Статус |
|---|---|---|---|
| **FR-048** | Служебные записки: подача любым сотрудником и согласование | MUST | **Реализовано** |

**Новые бизнес-правила:**

| ID | Правило |
|---|---|
| **BR-029** | Подать служебную записку может **любой сотрудник**. Маршрут согласования (BR-003): `PENDING_PM → PENDING_HR → APPROVED`, отклонение на любом этапе → `REJECTED`. Автор может **редактировать и отозвать** записку, пока нет финального решения |
| **BR-030** | Утверждённый больничный или отпуск **автоматически** проставляется в табеле; дни отсутствия уменьшают доступную ёмкость при расчёте индекса нагрузки |

**Типы записок:** `VACATION` (отпуск), `SICK_LEAVE` (больничный), `OTHER` (прочее).
**Статусы:** `DRAFT`, `PENDING_PM`, `PENDING_HR`, `APPROVED`, `REJECTED`, `CANCELLED`.

**Модель данных — `service_memo`:** `id`, `user_id` (FK), `memo_type`, `start_date`, `end_date`, `reason`, `status`, `pm_decision_by_id` (FK), `pm_decision_at`, `hr_decision_by_id` (FK), `hr_decision_at`, `rejection_reason`, `created_at`

## 12. ЭТИЧЕСКИЕ И ПРАВОВЫЕ ПОЛОЖЕНИЯ (дополнение к разделу 26.3)

1. Обработка персональных данных гражданина выполняется **с его согласия**, полученного при приёме на работу; момент согласия фиксируется в личном деле.
2. Обработка имеет **конкретную цель** — оформление трудового договора и ведение личного дела; данные не используются для иных целей.
3. Действует **принцип минимизации**: запрашивается только то, что необходимо для трудоустройства.
4. Доступ к персональным данным ограничен ролями ADMIN и HR; каждое обращение к госсистеме **протоколируется**, что позволяет установить, кто и когда получал данные.
5. В демонстрационной версии используются **только вымышленные данные** граждан.
6. Справочник сотрудников намеренно **не содержит** окладов, KPI и прогнозов риска — он доступен всем сотрудникам.
