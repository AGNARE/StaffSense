## Связанность фронта и бэка

| Показатель | Значение | Что это значит |

| View-эндпоинтов (`@*Mapping`) | 88 | каждый возвращает готовую HTML-страницу |
| Версионированных REST-эндпоинтов (`/api/v1/**`) | **0** | контракта для внешнего клиента нет |
| Вхождений `th:*` в шаблонах | 765 | разметка жёстко связана с моделями контроллеров |
| Вхождений `style="..."` в шаблонах | **285** | стили живут в разметке, а не в CSS |

**Вывод:** приложение — классический SSR-монолит без API-слоя. Разделение на
фронт и бек сейчас означает не рефакторинг, а написание 60–70 REST-эндпоинтов
и нового клиента на 38 экранов.

## Конкретные запахи

1. **Презентационная логика в контроллере.**
   `RiskController.java:195` — приватный `FeatureCardBuilder` с эмодзи-иконками,
   порогами «normal/warning/critical» и текстами описаний. Контроллер знает,
   как выглядит карточка признака, вместо того чтобы отдать данные.

2. **Доменные формулы раскиданы.**
   `workload_index` считается в `WorkloadCalculationService` и повторно в
   `AttritionMlService:209`, а также в генераторах датасета. Одна формула —
   три реализации.

3. **Дублирование правил между Java и Python.**
   Пороги риска вынесены в `RiskThresholdProperties` (хорошо), но формула
   эвристики-фолбэка продублирована в `AttritionMlService:287` и в
   `StaffSenseML/train.py` (как базовая модель).

4. **Инлайн-стили (285).** Дизайн-система из прототипа (токены, компоненты)
   не перенесена: каждая страница доопреденяет вид у себя.

5. **Сортировка в памяти.**
   `RiskController.java:61,87` — выборка страницы из БД по `fullName`, затем
   сортировка по риску в памяти. На 21 сотруднике незаметно, на 500 — неверно.

## Что НЕ является проблемой

- Пороги риска уже вынесены в конфигурацию (единый источник).
- Слои `controller → service → repository` соблюдаются: контроллеры не
  работают с репозиториями напрямую (кроме точечных случаев).
- Миграции Flyway дисциплинированы, схема валидируется (`ddl-auto: validate`).
